Brickie is written in Go, with a TypeScript demo and test suite that use the published SDK. The full guide is [CONTRIBUTING.md](https://github.com/hatchet-dev/brickie/blob/main/CONTRIBUTING.md) in the repository, and [AGENTS.md](https://github.com/hatchet-dev/brickie/blob/main/AGENTS.md) has the rules we work by. This is the short version.

## Before your first pull request

We only accept pull requests from people who have been [vouched](https://github.com/mitchellh/vouch). A pull request from anyone else is closed automatically. To get vouched, open a [vouch request discussion](https://github.com/hatchet-dev/brickie/discussions/new?category=vouch-request). Say what you want to change and why, in your own words. A maintainer replies with `!vouch`, and a pull request adds you to `.github/VOUCHED.td`.

Once you are vouched, start small. Keep one pull request open at a time, and tie it to one issue that has the `accepted` label. Good first changes are documentation, chart values, examples and small bug fixes. Changes to the engine, the drivers, the store layout, the wire contract, the TLS path or the release tooling come after a few of those.

If you used AI for any part of a pull request, issue or discussion, say so. The [AI usage policy](https://github.com/hatchet-dev/brickie/blob/main/AI_POLICY.md) has the rules, and the pull request template has a place to write it down.

## Build and check

```bash
go build ./... && go vet ./...
pnpm install && pnpm -r typecheck
```

Build binaries into `/tmp` or use `go install`. Binaries never get committed.

## Test

```bash
hack/run-demo.sh          # the demo session on the Docker driver
hack/run-demo.sh fs       # the file API
hack/e2e-kind.sh          # both demos on the Kubernetes driver in a kind cluster
hack/run-demo.sh up && (cd examples/typescript && pnpm test)   # the e2e suite
```

CI runs all of these on every pull request. Each one starts with `hack/ensure-sandboxd-image.sh`, which builds the pinned sandboxd image locally if its tag is not on GHCR yet. A pull request never publishes an image. The demos stay simple on purpose, and the detailed checks live in the e2e suite.

## Rules that are easy to miss

- Everything is FIPS 140-3. `brickie` is built with `GOFIPS140=v1.0.0` and `//go:debug fips140=on`, and `hack/check-fips.sh` fails the build otherwise. There is no non-FIPS variant.
- A published image tag is never overwritten. A fix ships under the next version.
- Log through `log/slog` only. `--log-format` picks JSON or text, and nothing writes to stderr directly.
- Task names have no colons. Hatchet action IDs are `workflow:task`.
- Snapshots are keyed by run ID so a retry overwrites its own snapshot. Replay safety depends on this.
- No environment variable from the host ever reaches a sandbox.
- The provider never touches a sandbox's files itself. Everything goes through sandboxd or runs as a command inside the sandbox.
- No code comments, except where the code cannot express a constraint on its own.

## Changelog and releases

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A change goes under `Unreleased`. When we release, that section becomes `## [version] - date`, and the release workflow reads its notes from there and refuses to ship without it. A section that has been released is never edited again.

A release is an annotated `v*` tag. The workflow builds the archives with goreleaser, pushes `ghcr.io/hatchet-dev/brickie`, signs it with cosign and attaches an SBOM. After that, the Helm chart in hatchet-charts needs its `appVersion` bumped. `sandboxd` and `agent-sandbox-controller` are rebuilt from the upstream release every day by `fips-images.yaml`.

## Security

Report a vulnerability through the [security policy](https://github.com/hatchet-dev/brickie/blob/main/SECURITY.md), never in a public issue.
