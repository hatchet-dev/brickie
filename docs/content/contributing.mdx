Brickie is Go, with a TypeScript demo and test suite on the published SDK. The repository's [CONTRIBUTING.md](https://github.com/hatchet-dev/brickie/blob/main/CONTRIBUTING.md) is the full guide and [AGENTS.md](https://github.com/hatchet-dev/brickie/blob/main/AGENTS.md) holds the working rules. The short version follows.

## Before your first pull request

Pull requests are only accepted from [vouched](https://github.com/mitchellh/vouch) contributors. Anyone else's pull request is closed automatically. Open a [vouch request discussion](https://github.com/hatchet-dev/brickie/discussions/new?category=vouch-request) that says what you want to change and why, in your own words. A maintainer answers with `!vouch` and a pull request adds you to `.github/VOUCHED.td`.

Once vouched, start small. One open pull request at a time, scoped to one issue with the `accepted` label. Documentation, chart values, examples and well-scoped bug fixes are the right first changes. Changes to the engine, the drivers, the store layout, the wire contract, the TLS path or the release tooling come after a few of those.

Every use of AI in a pull request, issue or discussion has to be disclosed. The [AI usage policy](https://github.com/hatchet-dev/brickie/blob/main/AI_POLICY.md) has the rules, and the pull request template has the disclosure block.

## Build and check

```bash
go build ./... && go vet ./...
pnpm install && pnpm -r typecheck
```

Build binaries to `/tmp` or use `go install`. Binaries are never committed.

## Test

```bash
hack/run-demo.sh          # the demo session on the Docker driver
hack/run-demo.sh fs       # the file API
hack/e2e-kind.sh          # both demos on the Kubernetes driver in a kind cluster
hack/run-demo.sh up && (cd examples/typescript && pnpm test)   # the e2e suite
```

CI runs all of these on every pull request. Each first runs `hack/ensure-sandboxd-image.sh`, which builds the pinned sandboxd image locally when its tag is not on GHCR yet. Pull requests never publish images. The demos stay simple and the concept checks live in the e2e suite.

## Rules that are easy to miss

- Everything is FIPS 140-3. `brickie` builds with `GOFIPS140=v1.0.0` and `//go:debug fips140=on`, gated by `hack/check-fips.sh`. There is no non-FIPS variant.
- A published image tag is never overwritten. A fix ships under the next version.
- Log through `log/slog` only. `--log-format` picks JSON or text and nothing writes to stderr directly.
- Task names contain no colons. Hatchet action IDs are `workflow:task`.
- Snapshot writes are keyed by run ID so retries overwrite their own snapshot. Replay safety depends on it.
- No host environment variables reach a sandbox.
- The provider never touches sandbox files itself. Everything goes through sandboxd or runs as a command inside the sandbox.
- No code comments except where the code cannot express a constraint.

## Changelog and releases

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A change goes under `Unreleased`. A release turns that into a `## [version] - date` section, which the release workflow reads and refuses to ship without. A released section is never edited.

A release is an annotated tag `v*`. The workflow builds the archives with goreleaser, pushes `ghcr.io/hatchet-dev/brickie`, signs it with cosign and attaches an SBOM. The Helm chart in hatchet-charts then needs its `appVersion` bumped. `sandboxd` and `agent-sandbox-controller` are rebuilt daily from the upstream release by `fips-images.yaml`.

## Security

Report vulnerabilities through the [security policy](https://github.com/hatchet-dev/brickie/blob/main/SECURITY.md), not in a public issue.
